Published: October 19, 2026 • 7 min read • By HookArmor Systems Team

When building high-volume webhook ingress proxies, throughput is rarely bottlenecked by CPU or disk I/O. Instead, it is almost always destroyed by two subtle system phenomena: TCP/TLS socket handshake overhead and database lock contention under instantaneous bursts.

1. The TCP & TLS Handshake Tax in Webhook Forwarding

In modern microservices and SaaS stacks, webhook providers like Stripe, Shopify, and Clerk send webhooks over HTTPS. When your ingress gateway receives a batch of 50 subscription renewals or checkout events, it must forward them downstream to your core backend API (e.g., https://api.yourcompany.com/webhooks/stripe).

In naive implementations using Node.js's standard http.request or default fetch() without connection pooling:

  • Every single dispatch negotiates a full TCP 3-way handshake (1 RTT).
  • Every single dispatch negotiates a complete TLS 1.3 cryptographic handshake (1–2 RTTs).
  • The socket is torn down immediately upon response completion (Connection: close).

If your destination server is located in a different availability zone or region (50ms round-trip), every webhook dispatch pays a 100ms to 150ms connection tax before a single byte of payload is transmitted.

The Keep-Alive Pooling Architecture

HookArmor 1.4.2 initializes persistent, connection-reusing agents inside the core Dispatcher: 

// src/dispatcher.js (v1.4.2)
this.httpAgent = options.httpAgent || new http.Agent({
  keepAlive: true,
  keepAliveMsecs: 10000,
  maxSockets: options.maxSockets || 50,
  maxFreeSockets: 10
});

this.httpsAgent = options.httpsAgent || new https.Agent({
  keepAlive: true,
  keepAliveMsecs: 10000,
  maxSockets: options.maxSockets || 50,
  maxFreeSockets: 10
});

When a batch of webhooks arrives, the first dispatch establishes the secure TLS tunnel. Subsequent dispatches reuse the hot socket instantly.

2. SQLite Burst Concurrency: Solving `SQLITE_BUSY`

HookArmor owes its sub-10ms ingress speed and zero-dependency footprint to embedded SQLite operating in Write-Ahead Logging (WAL) mode. When HookArmor acknowledges an incoming webhook with 200 OK, it executes with PRAGMA synchronous = FULL, ensuring the payload is physically fsynced to disk before returning to Stripe.

However, in high-volume environments (such as midnight subscription billing batches), multiple processes or threads can attempt write transactions simultaneously.

⚠️ The Default SQLite Busy Timeout Trap

In better-sqlite3, the default busy timeout is 0 milliseconds. If a write lock is momentarily held by an active commit, any concurrent transaction throws an immediate SQLITE_BUSY: database is locked exception rather than waiting.

In HookArmor 1.4.2, we enforce a strict 5,000ms busy wait timeout on database initialization: 

// src/storage.js
init() {
  try {
    this.db.pragma('journal_mode = WAL');
    // FULL fsyncs every commit: an event acknowledged with 200 OK survives power loss
    this.db.pragma('synchronous = FULL');
    // Wait up to 5,000ms for locks to clear before throwing SQLITE_BUSY
    this.db.pragma('busy_timeout = 5000');
  } catch (e) {}
}

With WAL mode enabled, readers never block writers, and writers never block readers. The busy_timeout = 5000 ensures that even during massive concurrent write spikes, transactions queue gracefully and commit with zero data loss.

3. Memory-Bounded FIFO Rate Limiting

HookArmor enforces in-memory rate limiting on webhook ingress, administrative auth attempts, and public waitlist signups. In standard fixed-window rate limiters, entries are stored in a JavaScript Map keyed by client IP.

During an adversarial distributed flood across tens of thousands of unique IP addresses within a single 60-second window, traditional expired-entry pruning cannot delete unexpired keys. This causes unbounded memory growth.

HookArmor 1.4.2 introduces a hard FIFO capacity cap: 

// src/server.js
function createRateLimiter({ limit, windowMs, maxKeys = 10000 }) {
  const hits = new Map();
  return (key) => {
    const now = Date.now();
    if (hits.size > maxKeys) {
      // 1. Prune legitimately expired entries
      for (const [k, v] of hits) {
        if (v.resetAt <= now) hits.delete(k);
      }
      // 2. Hard cap: discard oldest keys if still at capacity during active flood
      while (hits.size >= maxKeys) {
        const oldestKey = hits.keys().next().value;
        if (oldestKey === undefined) break;
        hits.delete(oldestKey);
      }
    }
    const entry = hits.get(key);
    if (!entry || entry.resetAt <= now) {
      hits.set(key, { count: 1, resetAt: now + windowMs });
      return true;
    }
    entry.count++;
    return entry.count <= limit;
  };
}

This guarantees that even under a massive 100,000-request multi-IP DDoS attack, the rate limiter's memory consumption is strictly clamped to a predictable footprint.

4. Zero-Downtime Hot Backups for SQLite WAL

Because HookArmor takes custody of the event after sending 200 OK to Stripe, persistent disk storage is mandatory. However, operators often ask: "How do I back up a live SQLite database without stopping the container?"

In WAL mode, running cp hookarmor.db backup.db on a live database is unsafe because uncheckpointed transactions reside in the hookarmor.db-wal file. A naive file copy can result in an inconsistent or corrupt snapshot.

The Production Online Backup Runbook

HookArmor 1.4.2 documents the official zero-downtime hot backup procedure using SQLite's native non-blocking Online Backup API: 

# 1. Atomic Hot Backup on Host (Runs while webhooks are actively ingesting)
sqlite3 /app/data/hookarmor.db ".backup '/backups/hookarmor-$(date +%Y%m%d_%H%M%S).db'"

# 2. Inside a Docker Container
docker exec hookarmor sqlite3 /app/data/hookarmor.db ".backup '/app/data/backup-$(date +%Y%m%d_%H%M%S).db'"

The .backup command acquires locks only for brief page copy intervals, checkpoints uncommitted WAL frames into the backup file, and produces a 100% verified, isolated snapshot without dropping a single incoming webhook.

5. Security Hardening: Strict WebSocket Invariants

In HookArmor 1.4.2, WebSocket connection authentication has been tightened:

  • Whenever HOOKARMOR_API_KEY is set, WebSocket connections always require token authentication (within a 5-second lease window). Demo mode or unauthenticated fallback flags can never override an active production API key.
  • Downstream failure response bodies stored in the Dead-Letter Queue are clamped to 2,000 characters and stripped of non-printable control characters, neutralizing malformed payloads before they reach the admin dashboard.
  • Downstream error messages included in Slack and Discord sentinel alerts are clamped to 500 characters to prevent alert payload bloat.
